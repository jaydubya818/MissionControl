# Relay factory pilot lessons and improvements

This is the living findings register for the first major project delivered through Mission Control's AI software factory. It covers the Relay product, its UI and UX, backend behavior, and the factory itself.

Bounded follow-up specifications are maintained in [`corrective-workorders.md`](./corrective-workorders.md), with the reviewed Relay contract direction in [`relay-contract-revision-plan.md`](./relay-contract-revision-plan.md).

## How to use this register

- Add findings when there is concrete runtime, browser, code, or operator evidence.
- Keep Relay product findings separate from Mission Control factory findings.
- Convert an actionable finding into a bounded, dependency-aware WorkOrder with explicit acceptance criteria.
- Record the WorkOrder or evidence link and move the status through `observed`, `queued`, `running`, `verified`, `deferred`, or `accepted`.
- Do not mark an item verified from an agent self-report alone.

## Relay product review queue

The contract-level review is below. A visual implementation review will follow after the foundation and dashboard WorkOrders produce a browser-operable build, covering:

- first-run comprehension and onboarding
- navigation and information architecture
- loading, empty, error, and success states
- permission and capability clarity
- memory, connectors, sandbox, and audit flows
- responsive behavior, accessibility, and visual consistency
- trust cues for agent actions, approvals, receipts, and failures

The pre-implementation contract audit already found that the current WorkOrders can pass with backend tests, route presence, and a generic shell screenshot. Before their dispatch, UI-bearing WorkOrders need deterministic browser criteria for:

- account creation, sign-in, session expiry/resume, sign-out, validation, and demo-mode boundaries
- agent creation, runtime attach/test/recovery, capability discovery, visible leases, and safe agent deletion
- permission grant, deny, revoke, renew, Computer lock ownership, and supervised handoff
- intentional loading, first-use empty, filtered-empty, permission-denied, degraded, fatal-error, and success states
- deep links, refresh, back/forward, active navigation, keyboard-only use, visible focus, announcements, contrast, and reduced motion
- desktop and tablet viewport coverage without clipped controls or horizontal page overflow
- Memory create/read/search/edit, conflict comparison/resolution, persistence, retention, and deletion feedback
- Connector test-before-grant, explicit grant, provider rejection/timeout/rate limit/revocation/open-circuit states, reconnect, and revoke
- Sandbox create/execute/result/stop, TTL warning/expiry, two-agent collision, and recoverable isolation failures
- Activity versus Audit distinction, useful filtering, receipt detail, correlation-driven diagnosis, approval consequence preview, and durable confirmation

One additional implementation owner is required: **WO-015 Browser/Computer Observer + Runtime Presence**, after WO-004, WO-005, WO-007, and WO-008. Its browser gate must prove one controller with read-only observers, denied second-controller acquisition with holder and TTL, audited supervised handoff, reconnect behavior, accessible status announcements, and absence of secrets from UI evidence.

- Standardize the fourth health state as `UNKNOWN`, matching normative Relay spec section 70, in the Mission Plan revision 2 contracts and implementations.
- Attach an authoritative token or reference-screenshot baseline to “preserve the original Relay design system language.”
- Add WO-008 as a dependency for Connector UI, WO-011 Sandbox UI, and the operator-facing portion of WO-007 Activity/Audit.

## Pilot-level lessons

- Contract revisions are execution boundaries, not metadata edits. Recovery must start a compatible attempt.
- Readiness and dispatch must share one decision path. Any disagreement destroys operator trust.
- Operator attention should be derived from actionable governance state rather than implementation task projections.
- Factory ownership and execution identity must project onto Tasks without a parallel legacy agent roster.
- A first factory project needs clean separation between live mission work, simulations, and stale runs.
- Verification evidence must remain bound to the exact revision, commit, workflow, and factory version that produced it.
- Repository scopes and WorkOrder change budgets must be checked for set compatibility before an executor is launched.
- A durable Attempt must never remain healthy only because its heartbeat loop survived the owned executor process.
- Certified harnesses need versioned runtime homes and caches; sharing mutable desktop-agent state breaks reproducibility.
- Worker identity is a frozen execution input. Reattestation and dispatch must update one canonical binding projection so readiness, claim, and operator UI cannot disagree about the active profile.
- Dependency preparation must not spend a full timeout probing an empty offline store, and long preparation phases must renew or replace stale checkpoints.
- Frozen verification commands must pass the effective executable and command-class policy before a human is asked to approve the revision.
- Process-based evidence wrappers must consume, redact, and retain bounded child stderr; an exit code without the launcher's diagnostic is not sufficient factory evidence.
