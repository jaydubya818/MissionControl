# Independent data-integrity review — current Convex liability skeleton

Reviewed 2026-09-05 by a separate agent using the data-integrity-guardian skill. Read-only review of source and captured evidence; no test execution, database writes, Docker, network or provider calls by this reviewer. This report describes the current Convex implementation and supersedes the earlier statement that no production-shaped transactional storage implementation exists. It does not supersede the pilot NO_GO disposition.

Scope: `convex/factory/providerLiability.ts`, `convex/lib/providerLiability.ts`, `convex/lib/providerLiabilityValidators.ts`, the three new schema tables, provider liability service-command actions, pure transition tests, actual handler tests, profile/lease helper linkage, and `liability-occ.json`.

## Recommendation

**NO_GO for pilot execution.** The new code establishes a useful transactional reservation skeleton and conservative balance rules. No critical concurrent balance-release or second-budget creation defect was identified in the inspected normal paths. The provider route is unselected, and the code/evidence do not yet qualify an actual broker send, provider billing behavior, full cohort authority or complete admission chain. Those remain admission blockers rather than failures of the narrow offline proofs.

## Concrete finding

**DI-C1 — Medium: correction can make a historical usage ID reusable.** `settleProviderUsage` pins a hold's `providerRequestId`, but an authorized correction can replace its `usageId`. Duplicate detection searches only current hold values; it does not consult the append-only usage events. For example, request A settles with usage U1, then an authorized correction for the same provider request replaces U1 with U2. Request B can subsequently settle with U1 and a distinct provider request ID, although an earlier persisted event already used U1. This compromises the claim of historical usage-ID replay protection. Full maximum holds remain encumbered, so this finding does not release capacity or establish a spending-limit bypass.

Close by keeping each hold's usage ID immutable if that matches the admitted provider contract, or by checking a persistent receipt-identity registry/history atomically before accepting replacement or reuse. Add a correction-then-cross-request-replay regression. If providers require changing usage IDs on corrections, preserve every prior binding and make the supersession semantics explicit.

## Integrity controls supported by source inspection

- **One budget per WorkOrder.** Creation checks both the project/idempotency-key index and `by_work_order` within the same Convex mutation before insert. The second check includes expired reservations and all revisions/profiles, preventing a fresh key or revised WorkOrder from silently granting a second balance. The same index range is read before concurrent inserts, supporting the observed OCC conflict behavior. This is application-enforced uniqueness, not a declaration that a Convex index itself is unique.
- **Atomic reservation.** A single mutation reads the reservation and writes the updated snapshot. Competing requests conflict on the shared row. The transition re-evaluates available capacity from current holds on retry. Request replay is denied before adding a hold.
- **Conservative capacity.** Every hold continues to consume at least its full maximum after settlement, unknown usage and corrections. Accounted cost above that maximum increases encumbrance. No settlement, expiry, correction or uncertain result frees capacity. The 100-request upper bound keeps embedded hold arrays bounded. A lower proposed pilot attempt/retry ceiling still needs its own final integration.
- **Scope and current worker checks.** Request mutations load the actual reservation and run, require their project/WorkOrder match, current WorkOrder execution and revision, eligible profile, RUNNING status, no cancellation, exact lease and generation, unexpired lease, execution-profile digest and repository match. `factoryLeaseMatchesCurrentRegistration` also checks the current host worker/session/generation. The reservation ceiling must fit the run's frozen Factory version cost limit. Profile eligibility is loaded again per request rather than trusted from creation alone.
- **Immutable price linkage.** Registration validates bounded shape, identities, integer rates/token limits, timestamps, evidence digest and inclusive billing assertions. Creation compares provider/model to the profile route, verifies price digest, and prevents the reservation outliving price/profile validity. Reserve recomputes the price digest against the reservation. These are governance assertions and cryptographic identity checks; an HTTPS source plus a digest is not proof that an external provider honors a bound.
- **Replay and receipts.** Request digest, provider/model, hold identity and receipt revision are checked. Exact duplicate receipt content is idempotent; conflicting revision updates fail. Worker settlement additionally binds the held request to Attempt/lease/generation. Ordinary current-state reuse of provider request IDs and usage IDs across holds is rejected. DI-C1 identifies the remaining historical usage-ID correction gap.
- **Unknown and overrun handling.** UNKNOWN preserves maximum liability. Usage above the request's input/output or monetary bound is persisted as OVERRUN and freezes the reservation. A later correction does not automatically clear the freeze. Correcting a settled/overrun hold requires the public operator reconciliation path, not the worker path. Token counts can be classified ACTUAL while derived monetary cost remains ESTIMATED; this avoids representing calculated token-rate cost as an invoice-confirmed charge.
- **Atomic audit trail.** Usage snapshot updates and event inserts occur in one mutation. Correction events retain the supplied evidence reference, actor, receipt and incident state. Immutable price/reservation creation records retain actor, time, key and creation digest. No new deletion, balance reset or unfreeze operation was observed.
- **Authorization boundaries.** Public register/create/reconcile operations require workspace automation-management permission; reads require workspace view permission. The two service actions verify a signed, scoped capability envelope, claim an idempotency receipt, and dispatch to internal mutations. Mutations still recheck current authority. Action receipt completion and reservation mutation are separate transactions: a failure after reservation may strand an authorized hold, but replay checks and retained capacity favor denial rather than another send. Recovery of that uncertainty remains broker integration work.

## Evidence assessment

The pure tests exercise bounded price/request rejection, reservation expiry, scope fencing, retained maximums, receipt revisions, ordinary replay, unknown usage and overrun freeze. The actual handler tests invoke the real handler functions with mocked database/auth/profile-admission dependencies and exercise current run/revision, cancellation, lease, generation, host session, profile, repository and Factory-budget guards. They do not execute the complete profile admission implementation or signed service-action flow end to end. The implementer reports 39 passing tests; this reviewer inspected source rather than rerunning them.

`liability-occ.json` explicitly identifies a disposable isolated Convex backend, zero provider calls and fixture-only scope. It records one fulfilled and one rejected concurrent budget creation, and one fulfilled and one rejected full-balance request, leaving one maximum-30 hold. That supports the production-shaped index/read/write and shared-row OCC pattern. It does not establish that the exact complete public admission handlers were exercised on a real pilot profile, nor does it certify provider behavior. The artifact labels make this distinction correctly.

## Remaining production limitations

- The skeleton lacks an admitted live provider/broker path proving that every transmitted payload and output cap exactly matches its reservation. Real input token bounds, price semantics, request/usage identities and provider response guarantees remain unresolved. No live calls or real pilot reservations should be inferred from tests.
- There is one WorkOrder authority, not yet an enforced cohort balance or complete producer/verifier split. The frozen Factory ceiling check prevents a reservation exceeding that version's maximum; it does not implement every proposed pilot monetary and attempt restriction.
- Late usage after lease expiry, cancellation or terminal status cannot use the worker settlement endpoint because it deliberately rechecks current authority. Operator reconciliation is the available source path and retains evidence. Full operational delivery/recovery of late receipts remains unqualified; unresolved holds stay charged at their maximum.
- The new tables are additive; no migration or existing-row destruction was observed. Rollback must preserve any future reservations, holds and usage history, even if the broker is disabled. Do not remove state to regain capacity. Cross-record referential integrity is enforced by handler reads and matching checks, not database foreign-key constraints.
- Price assertion authority, reconciliation trust, provider receipt provenance and cross-reservation/provider-account usage identity still require the final governed broker design. The skeleton must not be presented as complete end-to-end hard-budget qualification.

The narrow transactional controls are meaningful progress. The correction replay finding and remaining provider/cohort/admission integration prevent promoting them to pilot readiness.

## Remediation re-review

**DI-C1 is closed in the updated source.** `settleProviderUsage` now rejects a changed previously recorded `providerRequestId` or `usageId` before duplicate detection, UNKNOWN handling or correction transitions. An authorized correction cannot replace the first recorded identity and make its historical usage ID reusable. The added regression asserts that attempting to replace the usage ID on a settled hold throws `USAGE_IDENTITY_CHANGED`. The existing cross-hold identity checks continue to apply. This means a future provider contract requiring receipt-identity changes must introduce explicitly reviewed supersession semantics, not bypass this guard.

The implementer reports the latest suite at **42 passing tests: 24 pure transition tests and 18 actual handler tests**. This reviewer inspected the remediation and regression source without executing them. No unresolved critical balance-integrity defect was identified in the bounded skeleton review. **NO_GO remains unchanged** because actual provider/broker proof, cohort restrictions and complete admission integration are still unqualified; the earlier DI-C1 paragraphs are preserved as review history rather than a currently open source defect.
