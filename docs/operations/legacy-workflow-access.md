# Legacy workflow access

Global legacy workflow definitions are read-compatible templates. They cannot be changed through public mutations or executed without an authorized workspace. `workflows:upsert` is now internal. Public production registration requires workspace automation-management permission and the structured workflow contract.

The built-in seeder requires explicit `CONVEX_SELF_HOSTED_URL` and `CONVEX_SELF_HOSTED_ADMIN_KEY` deployment-administrator configuration. `pnpm run workflows:seed` invokes the Convex CLI with credentials in the environment. It does not use anonymous public writes. Configure and verify the intended deployment before running it; this change does not authorize production or tester changes.

A deployment administrator can retire an unowned global definition through internal `workflows:retireLegacy`. It refuses project-owned definitions and any PENDING, RUNNING or PAUSED run referencing the definition directly or through a frozen snapshot. After controlled retirement, an authorized workspace owner can register a validated project definition with that identity. Public callers cannot adopt an ambiguous global row. Existing-data inventory, explicit identity mapping and rollback/data snapshots remain prerequisites for staging migration.

Direct v1 workflow runs require an explicit workspace and automation-management permission. Global templates and deterministic v2 workflows are unavailable in the direct-start chooser; governed Work starts through canonical WorkOrder dispatch. Canonical WorkOrder revisions and linked Tasks cannot bypass that route through direct start. Legacy run reads and writes require workspace permission, while existing Mission grants retain their exact scoped authority.


Runtime v67 also protects legacy Tasks, transitions, events, artifacts, activities and metrics through the shared database boundary. Reads require workspace visibility; delivery edits require delivery permission, and workflow control requires automation management. Historical WORKFLOW_STARTED input is removed from returned activity metadata; new activities omit it. Public Task transitions record the authenticated subject and cannot use a client human label as approval authority. Exact Mission grants retain their existing lineage checks.

All seed and E2E administration modules, WorkOrder demo installation and software-factory demo project creation are internal deployment-administrator operations. The public portfolio now leads to real Missions instead of fabricating demo Work and receipts. Run administrative seeds only against a verified disposable or explicitly authorized target; no installation command is implied by opening the UI. CLI workflow operations and the standalone executor require CONVEX_SERVICE_AUTH_TOKEN. Executor startup no longer seeds data; bootstrap is an explicit separate administrator action.

Global legacy templates are read-only compatibility data. Loop Engineering, continuous-research and feature-dev callers must migrate to a registered project-owned structured workflow and its qualified Factory before dispatch. They do not retain a global execution bypass. Inventory existing definitions and active direct/snapshot references, capture a data snapshot and rollback targets, then have the administrator retire an unused global identity and an authorized owner register its validated project definition. Existing-data mapping is a staging prerequisite; no automatic adoption or activation occurs.
