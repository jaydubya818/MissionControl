## Repairs prepared

### 1. Incomplete qualification could look successful

`scripts/system-factory-e2e-qualification.mjs` previously wrote a success-looking
receipt after successful intermediate commands. Killing a later command could
leave that earlier PASS as the apparent result. Independent review also found
that a startup Git metadata failure could leave an older receipt in place.

The repair writes RUNNING before metadata lookup or commands, records expected
and completed counts, leaves `completedAt` null while running, and writes PASS
only after every expected command succeeds in order. Failed setup, spawn errors,
signals, and command failures are retained. Each receipt replaces the prior file
through an atomic rename. New receipts use schema v3; historical evidence stays
unchanged.

Thirteen regression tests cover actual runner subprocesses with controlled
command outcomes, including interrupted execution and prior-receipt replacement.
This proves reporting behavior. It is not live application-generation evidence.
Concurrent qualification runs sharing an evidence destination and filesystem
durability under storage failure were not qualified by this repair.

### 2. TypeScript jobs depended on an unsuitable launcher

The automation adapter used `pnpm exec tsx`. On this host, the `tsx` CLI failed
while creating its IPC socket, before running the approved artifact. A new
negative control also showed that the original launcher could select a fake
executable from a candidate-controlled PATH.

The repaired adapter uses the worker's absolute Node executable and resolves the
installed TypeScript loader from the orchestration module. It passes the approved
absolute artifact path as an argument. Existing hash, path, timeout, cancellation,
process-group, and redaction behavior remains in place.

Fourteen tests pass, including a real TypeScript enum, a relative import, paths
with spaces, a nested working directory, candidate fake executables, and a
candidate-owned loader. A reviewer reproduced and corrected a test expectation
for symlinked temporary directories. Compilation and a plain-Node import of the
compiled ESM adapter also passed. Some author/reviewer checks were retained in
tool output and summarized in the accompanying runtime note; they are not raw
log files in the bundle.

The composed factory test generated a separate `tsx` CLI invocation. Its launcher
now uses the same trusted Node/loader approach while continuing to run Node's
actual test runner and the same assertions. Its four scenarios pass. The complete
pinned dependency installation remains required; this change does not qualify a
deployment that omits the existing development dependency on `tsx`.

### 3. Dependency preparation could not find the host package manager

The dependency installer intentionally uses a restricted PATH. This host's
installed pnpm lives outside that PATH. The resulting ENOENT was hidden because
empty stderr was selected instead of the error message.

The repair adds optional host configuration,
`MISSION_CONTROL_FACTORY_PNPM_CLI_PATH`. It must identify an absolute regular
file outside the candidate's lexical and canonical roots. The worker resolves
that file and launches it through its own Node executable. Candidate-local
paths and symlinks into the candidate are rejected. Unset configuration retains
the original lookup behavior.

The installer still uses a scrubbed environment, temporary HOME, a frozen
lockfile, disabled lifecycle scripts, disabled pnpm hooks, and source-state
checks. Diagnostics retain the error code and the first nonempty process detail.
Twenty focused tests pass, including the actual pinned pnpm installer against
malicious candidate hooks. The intentional unconfigured control still fails,
now with an actionable ENOENT diagnostic.

The recipe recommender checked high-risk subject words before the requested
action. A question about authentication and a request for a schema-migration
plan therefore recommended the full development workflow. This affected the
default selection in a Mission draft; it did not demonstrate dispatch or an
authorization bypass.

The bounded repair considers clear research, planning, and known-check requests
before subject risk. It distinguishes common negations and plan subjects from
separate positive change clauses. Actual mixed sensitive-change requests retain
the stronger workflow. The recommendation shape, operator override provenance,
and draft-only payload remain unchanged.

The new collision suite first produced nine expected failures against the old
source. Independent review then found three mixed-request regressions in the
first repair. Those failures were reproduced and corrected. The final catalog
and existing dialog component pass **32 focused tests**, including an
independent rerun and direct regression/control probes. UI typechecking passes.
This is an advisory heuristic, with no claim of
complete natural-language understanding. Visible browser behavior remains
**UNVERIFIED**. The attempted browser fixture could not establish a usable
browser session; jsdom component assertions do not close that gate.

### 5. Backend application changes could be labeled as UI

The semantic review grouping rule classified all `apps/*/src` files as UI,
including orchestration workers and dependency-preparation code. The repair
removes that broad assumption. Explicit component/view/style directories and UI
file extensions still classify as UI; files without sufficient evidence can
remain in the existing Other group. Authentication precedence, raw diff
lineage, and the advisory status are preserved.

Seven regression cases cover real backend paths and representative UI paths.
The original rule failed three of those cases. The repaired 13-test Review
Intelligence suite passes, including an independent rerun. This changes review
presentation data, not acceptance or execution authority.

### 6. Legacy GitHub imports lacked an authenticated project boundary

The public issue upsert could find an existing issue by a global key and update
it without resolving the caller or matching the stored project. A controlled
probe updated a task in one project while attributing the activity to another.
No hosted data was accessed by this probe.

The repair requires a real authenticated operator and existing workspace
permissions across the module's public helpers. Task-ID operations derive the
project from the stored task. Imports and edits require `delivery.write`.
New issue keys include project scope and normalized repository identity;
same-project legacy keys can be adopted, while another project's task is not
returned or changed. An authorized second project can import its own record.

Remote issue-state changes check the task's stored repository and issue number
before provider budget or network effects. PR links now retain their repository
separately, preventing a cross-repository PR from retargeting the linked issue.
The direct replay helper remains authenticated operator replay, not trusted
external webhook ingress. Eight repaired exports leave the legacy inventory.

### 7. GitHub synchronization silently stopped after one page

The original importer requested 100 GitHub entries once and reported success
even when a next page existed. The repair fetches and validates up to ten pages
before imports, retains PR filtering, and fails explicitly for malformed pages,
provider failures, unsafe pagination metadata, or more pages beyond the bound.

Official GitHub documentation exposed an additional compatibility case during
review: next links may use a canonical numeric repository path. The corrected
implementation extracts a validated page number and reconstructs the request
on the original repository endpoint. A pagination URL never selects another
credential destination, and redirects are rejected.

All fetched pages validate before imports. Per-issue writes are subsequently
separate operations, so a later failure can leave completed imports. The action
fails and retries use scoped keys; no transaction-wide rollback is claimed.
The existing shared task-creation budget remains in force. Ten pages is a fetch
limit, not a promise to create 1,000 tasks in one call.

The two GitHub repairs have 40 new behavioral cases plus 23 existing provider-
action checks: **63 focused tests**, including an independent rerun. The tests
use the real authorization helpers with controlled database/provider boundaries.
The INBOX task-creation boundary is a fixture and does not exercise the deployed
creation budget. The retained failures include the initial 28 failures, three
canonical-pagination regressions, and the PR-repository binding regression.
See [the GitHub intake note](../testing/github-issue-intake.md) for exact limits.

The integrated UI typecheck caught one cross-package typing issue after the
Convex check passed: its compiler settings retained the parsed issue body as
`unknown`. An explicit string normalization after the existing validator fixes
the type boundary without changing accepted values. The failure was retained,
the focused suite passed again, and an independent reviewer confirmed the
one-expression correction.

### 8. Improvement measurements assumed that larger values were better

The measurement helper always compared `result >= target`. For an intended cost
ceiling of 5, a result of 4 was marked missed and 8 was marked met. The repair
adds explicit `HIGHER_IS_BETTER` / `LOWER_IS_BETTER` target direction through the
helper, mutation, stored measurement, and activity metadata.

Omitted direction retains the historical higher-is-better meaning. Cost and
latency callers must explicitly select the lower direction; unit text is not
interpreted as policy. Older records remain valid and are not recalculated.
Nonfinite values are rejected before writes. Existing permissions, linked work,
evidence requirements, and deduplicated follow-up behavior remain in force.

### 9. Learning comparisons omitted retained quality scores

The experiment API already stored `averageScore`, but the Learning query dropped
it before generating its advisory recommendation. A diagnostic case with equal
success/duration, lower cost, and a score drop from 0.95 to 0.20 recommended
promotion because only cost reached the comparison.

The repaired projection retains the score. A known paired score regression
produces `REJECT_RECOMMENDED`; one-sided or invalid score evidence holds an
otherwise positive recommendation and provides comparison warnings. If both
scores are absent, the previous comparison of other metrics remains available,
without establishing quality preservation.

The two measurement repairs pass **39 focused tests**, independently rerun.
They exercise the actual registered query/mutation handlers with controlled
records and a permission adapter. The result still declares `autoPromote: false`
and `statisticallySignificant: false`. Shared experiment metadata and manually
entered aggregates do not prove matched replay cases or live improvement.
See [the measurement note](../testing/factory-measurement-semantics.md).

## Prepared to-do acceptance contract

The requested workload is documented in
[the qualification plan](../plans/2026-11-26-no-touch-factory-qualification.md).
It requires creation, edit/save/cancel, completion, reopening, deletion,
All/Active/Completed filters, and correct remaining counts. Titles must be
trimmed, have 1-200 characters, render as literal text, and visibly reject blank
input. Unicode, empty states, keyboard use, accessible names, and narrow-screen
layout are included. Browser-local persistence is sufficient and must survive
reload and reopening in the same browser profile.

The added article prompted an explicit persistence-failure check. If the browser
cannot save task state, the application must surface that failure rather than
claim successful persistence. Browser runtime errors and that failure path are
part of the required application evidence.

Independent browser verification must cover the exact candidate produced by the
real executor. Producer and verifier identities, WorkOrder/Attempt IDs, runtime
identity, provider provenance, source revision, and artifact digest must be
retained. The producer cannot change the acceptance suite to accept its own
output. A repaired run must preserve failed Attempts and receive fresh
verification.

Owner interactions and assistant interventions outside the factory must be
counted separately. The assistant's source repairs in this session do not prove
that the factory repaired itself. A clean repeat run after repairs is needed
before calling this workflow unattended.
